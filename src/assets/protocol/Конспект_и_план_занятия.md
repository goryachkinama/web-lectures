# Интернет — это не только HTTP

**Лекция-практикум по веб-разработке · 90 минут**  
Аудитория: студенты, уже знакомые с HTML, JavaScript, `fetch()`, HTTP, REST и базовой клиент-серверной архитектурой.  
Результат: студент способен выбрать модель обмена данными для типичной задачи и объяснить, где в веб-системе действительно используются разные сетевые протоколы.

## Замысел

**Не читать энциклопедию протоколов.** Строить разговор от знакомого `fetch()` к более богатым схемам взаимодействия: клиент опрашивает сервер, сервер отправляет поток событий, клиент и сервер поддерживают двусторонний канал, два браузера передают медиа, backend общается с устройствами, брокерами, почтой и другими сервисами.

Основная модель для студентов:

1. **Где выполняется код:** браузер, backend, мобильный клиент, устройство?
2. **Кто и как общается:** запрос-ответ, поток в одну сторону, двусторонние сообщения, publish/subscribe, RPC?
3. **Какие свойства нужны:** задержка, порядок, гарантированная обработка, устойчивость при разрыве, стоимость поддержки?

### Перед лекцией

Установить Node.js 20+ и браузер Chrome или Firefox. В папке `protocol-lab` выполнить `npm install && npm start`, открыть http://127.0.0.1:3000. Проверить, что панели Polling/SSE/WebSocket показывают общие числа. Проверить, что браузерные Developer Tools → Network доступны на проекторе. Если интернет может быть нестабилен, заранее выполнить `npm install` на компьютере преподавателя. Показывать все примеры с `127.0.0.1`, сервер не публиковать публично.

## Подробный сценарий преподавателя

### 0–10 мин: мотивация (слайды 1–2)

Начать с вопроса: **«Всё, что мы делали в веб-разработке, — это браузер, запрос на сервер, JSON в ответ. Как сделать чат без перезагрузки? А видеозвонок? А подписку на события от датчиков?»** Дать студентам сначала предложить polling. Это корректный старт, а не «ошибка». Затем спросить: что будет, если миллион пользователей каждые 200 мс проверяют новые сообщения? Не нужны точные расчёты — важна идея цены опроса и неизбежной задержки.

### 10–20 мин: архитектура и сетевые уровни (слайды 3–6)

Разделить понятия: протокол приложения (HTTP, SMTP, MQTT), транспорт (TCP, UDP, QUIC), API браузера (`fetch`, `EventSource`, `WebSocket`, `RTCPeerConnection`, `WebTransport`). DNS — прикладной протокол разрешения имен, а не «ещё один транспорт».

Показать характерные стеки: HTTP/1.1 и HTTP/2 обычно используют TLS над TCP; HTTP/3 — QUIC поверх UDP. QUIC сам обеспечивает надёжные потоки и механизмы восстановления, поэтому **HTTP/3 не становится «ненадёжным HTTP» из-за UDP**.

Подчеркнуть границу: браузерный JavaScript не может просто создать обычный TCP/UDP-сокет на произвольный адрес. Сервер на Node.js, Go и т. п. может использовать необходимые сетевые библиотеки. Отсюда идея **backend как адаптер протоколов**.

### 20–35 мин: модели реального времени (слайды 7–10)

**Polling**: отдельные HTTP-запросы через фиксированный интервал. Прост, но влияет на задержку и нагрузку. Дополнительно устно упомянуть *long polling* как ожидание события в рамках ответа на запрос.

**SSE / Server-Sent Events**: один долгий HTTP-ответ с `Content-Type: text/event-stream`, последовательными `data:`/`event:`/`id:`. Сервер отправляет события в браузер. `EventSource` автоматически пытается переподключиться. SSE — **не отдельный транспортный протокол вместо HTTP**. Отправить действие от браузера серверу можно отдельным `fetch(POST)`.

**WebSocket**: двусторонний поток **сообщений**. Для учебного примера используется HTTP/1.1 `Upgrade` → `101 Switching Protocols`; после установления идут WebSocket-фреймы. Есть и стандартизированные способы запуска WebSocket через HTTP/2 и HTTP/3, поэтому избегать категоричного «WebSocket всегда делает Upgrade и получает 101».

Дополнительно: бинарные данные возможны и в WebSocket. WebSocket сам по себе не гарантирует бизнес-доставку, сохранность или восстановление сообщений после потери соединения.

**Минимальный клиентский код:**

```js
// Polling
setInterval(async () => {
  const state = await fetch('/api/state').then(r => r.json());
  console.log(state);
}, 3000);

// SSE (сервер → браузер)
const events = new EventSource('/events');
events.addEventListener('update', e => console.log(JSON.parse(e.data)));

// WebSocket (в обе стороны)
const ws = new WebSocket('ws://127.0.0.1:3000/ws');
ws.onmessage = e => console.log(JSON.parse(e.data));
ws.onopen = () => ws.send(JSON.stringify({type: 'increment'}));
```

### 35–50 мин: живая демонстрация (слайд 11)

1. Открыть http://127.0.0.1:3000 и *DevTools → Network*. Включить **Preserve log**.
2. Найти `GET /api/state`: каждые три секунды появляются новые запросы. Спросить, почему числа в панели Polling иногда отстают.
3. Найти `/events`: запрос не завершается, заголовок `text/event-stream`. В EventStream/Response видно несколько событий в рамках одного ответа. Можно показать в терминале `curl -N http://127.0.0.1:3000/events`.
4. Найти `/ws`: посмотреть Handshake и Messages (в некоторых браузерах вкладка Frames). После соединения видны сообщения от сервера.
5. Нажать **HTTP POST**: все клиенты увидят изменение, но SSE ничего не отправлял на сервер.
6. Нажать **WebSocket send()**: команда от браузера к серверу появится в WebSocket Messages. Обновления увидят и другие вкладки.
7. Спросить: что будет при временной потере сети? Для SSE браузер попытается восстановить EventSource, а WebSocket в демонстрации останется закрытым, пока приложение не создаст новое соединение.

**Важно про измерение «задержки»:** в демонстрации измеряется время от создания последнего состояния до его обработки конкретным клиентом. Это **не** точная end-to-end network latency; для учебного сравнения свежести данных достаточно.

### 50–60 мин: WebRTC и WebTransport (слайды 12–13)

**WebRTC** — набор браузерных возможностей для передачи аудио, видео и произвольных данных между участниками. Для установления соединения требуется сигнализация (её можно реализовать через WebSocket/HTTP), а STUN/TURN помогают с сетевым маршрутом. WebRTC **не гарантирует прямой P2P во всех сетях**: TURN может выступить ретранслятором.

**WebTransport** — современная браузерная технология на базе HTTP/3/QUIC: несколько независимых потоков и датаграммы. Подходит для некоторых latency-sensitive сценариев, но требует поддерживаемого браузера и сервера, а также значительно более сложной инфраструктуры. **Это не открытый UDP-сокет**. Не делать основной практикум на WebTransport: слишком много ограничений для вводной лекции.

### 60–75 мин: другие протоколы на стороне backend (слайды 14–17)

**MQTT:** устройство публикует данные в топик, брокер доставляет подписчикам. Веб-backend может получать данные от брокера и отправлять обновления браузерам по SSE/WS. MQTT-клиент из браузера существует, но обычно использует **MQTT поверх WebSocket** и требует соответствующей настройки брокера, а не произвольный `mqtt://` TCP-коннект.

**SMTP:** после регистрации пользователь отправляет HTTP POST на backend, backend или worker передаёт задачу почтовому провайдеру по SMTP либо через HTTPS API. Не размещать SMTP-учётные данные в клиентском JS и не пытаться напрямую подключать браузер к SMTP-сокету.

**gRPC:** RPC-подход, обычно Protocol Buffers поверх HTTP/2. Стандартный gRPC в обычном браузере напрямую ограничен особенностями HTTP/2 API. Для браузеров применяется gRPC-Web с адаптацией (часто через proxy). Официальный grpc-web поддерживает unary и server-streaming, но не client-streaming и полноценный bidi-streaming. Следовательно, «gRPC» — **не конкурент HTTP на одном уровне протокольного стека**.

Если студенты уже проходят backend, в качестве дополнительных примеров можно назвать AMQP/RabbitMQ, Redis RESP, PostgreSQL wire protocol, SSH/SFTP и DNS. Не разбирать их все подробно в основной лекции.

### 75–85 мин: критерии выбора и упражнения (слайды 18–20)

Один протокол не устраняет авторизацию, проверки Origin, периодические проверки связи, reconnect с backoff, дубли, потерянные события, контроль очередей клиента, idempotency и сохранение критичных сообщений. Особенно важно различать **«байты дошли»** и **«бизнес-операция гарантированно обработана»**.

Раздать четырём группам по сценарию:

- **A.** Показывать процент обработки долгого отчёта. Подход: SSE + отдельные HTTP-команды; polling может быть достаточен.
- **B.** Совместно редактировать документ. Подход: WebSocket + согласование конкурентных изменений (не решается одним транспортом).
- **C.** Получать показатели с 1000 датчиков. Подход: устройства → MQTT-брокер → backend → SSE/WebSocket.
- **D.** В личном кабинете показывать редкие уведомления. Подход: обычный polling с приемлемым интервалом, либо SSE при строгих требованиях к оперативности.

Каждая группа должна объяснить, почему она выбрала подход, а не просто назвать технологию.

### 85–90 мин: квиз и закрепление (слайды 21–23)

| Утверждение | Ответ | Почему |
|---|---|---|
| SSE не зависит от HTTP | Ложь | Это формат событий в HTTP-потоке |
| WebSocket двусторонний | Правда | Обе стороны отправляют сообщения по открытому каналу |
| Страница может открыть обычный raw TCP-сокет к SMTP | Ложь | У браузера нет произвольного TCP socket API |
| WebRTC всегда напрямую соединяет браузеры | Ложь | Возможен путь через TURN |
| gRPC-Web умеет любой двусторонний streaming | Ложь | В официальном grpc-web есть ограничения |

**Заключительный тезис:** сначала определяем задачу, затем модель коммуникации и эксплуатационные требования, и только потом выбираем протокол и библиотеку.

## Практическая работа после занятия

**Задание:** расширить проект `protocol-lab` и оформить небольшой ADR (архитектурное решение): «Как доставлять обновления о статусе обработки задач». Необходимо показать не менее двух вариантов и аргументировать выбор.

**База (до 30 минут):** поменять интервал polling; измерить число HTTP-запросов за минуту; добавить вывод времени последнего сообщения.

**Уверенный уровень (до 60 минут):** добавить именованные SSE-события `alert` и `progress`, обработать их по-разному.

**Продвинутый уровень (до 1,5 часа):** реализовать reconnect WebSocket с ограниченным exponential backoff, повторную подписку и обработку пропущенных событий по ID; объяснить границы надёжности.

**Критерии оценки:** корректность работы (40%), объяснение выбора и ограничений (35%), поведение при обрыве и ошибках (25%).
